## Phase 1 — Read the paper and write the overview (inline)

No subagent: a paper fits the orchestrator's context, and Phase 2 needs the section map anyway.

**Obtain the text** by running `bash <SKILL_DIR>/scripts/preflight.sh bash <SKILL_DIR>/scripts/mineru_ocr.sh <pdf-abs-path> <WORK_DIR>/ocr` (the `preflight.sh` wrapper resolves the python3+poppler env — PATH or the bundled flake — then execs `mineru_ocr.sh` inside it). It writes `ocr/paper.md` with one `[pNN]` anchor per page — the body text refilled from the PDF's text layer over MinerU's block skeleton (see the Gotcha above), with inline math as `$…$` LaTeX and section headings from MinerU's title blocks. It extracts figures/tables to `ocr/figures/` named by their paper reference number (`fig-NN.<ext>` / `table-NN.<ext>`, e.g. `fig-03.jpg` = Fig. 3), already referenced from `paper.md` by relative path, and writes `ocr/figures.md` — a metadata index mapping each image file to its label, page (`[pNN]`), and caption. (The number comes from the block caption; a caption MinerU dropped is reconstructed from figure order. Because the filename no longer encodes the page, `figures.md` is the authoritative file→page map for Phase 2 assignment.) Tables are kept as both the cropped image and their cell text (`<table>` HTML), so numeric results survive in the text stream. Footnotes are preserved as GitHub-flavored footnotes — a body reference as `[^N]` and its definition as `[^N]: …` — so the body↔footnote link is kept. This covers both numeric footnotes and symbol footnotes (`∗`/`†`/`‡` author/affiliation notes, label e.g. `[^star-p01]`, page-scoped since symbols are reused across pages). If MinerU located a figure/table but could not extract it, `figures.md` ends with a "⚠ Not extracted" section listing it for Finalize recovery (the script also prints a `⚠ N figure/table(s)…` line). MinerU can take minutes — run it with a generous timeout. Then Read `ocr/paper.md`. On failure, report the error and stop — do not fall back to another reader (a missing `mineru` should already have stopped the run at Prerequisites).

**Extract while reading:**
- Bibliographic metadata: title, authors, venue/journal, year, DOI or arXiv URL — **only what is printed in the paper**; if the venue is not printed (arXiv preprint), write "不明 (preprint)" rather than guessing.
- A section map: every source-authored section with its `[pNN]` span, including
  the References span (Phase 2 needs it). Preserve each heading's source form and
  level; this map is also materialized as `source-structure.md` below.
- **A running-example map — only if the paper leans on one worked/running example that more than one perspective will discuss.** Build it once, here — but note the trap: once handed down, this map is the *single source* for every report that uses it, so an error in it propagates to all of them and no cross-report check can catch it (the reports will agree, on the wrong thing). Single-sourcing removes the divergence that would otherwise flag a mistake, so the map must be right at construction, not merely consistent. Build it against ground truth, not prose:
  - **Open the original figure image in `ocr/figures/` with the Read tool** (do not build the map from the OCR sentence — multi-column OCR scrambles word order and swaps which object is looked up by which key, e.g. "a B is retrieved by its id from a previously fetched A").
  - One row per distinct example feature: `feature (the exact code token / label as it appears in the figure) → the concept/label the paper attributes it to → the figure element you read it off (label / arrow / callout) → [pNN]`. The evidence column is mandatory — it forces each attribution to be anchored to something visible in the image and makes the map auditable.
  - **Where the figure and the OCR prose disagree, the figure wins**; note the correction. A row you cannot anchor to a visible figure element is written "(要確認)", not asserted.
  - **Before recording the map, re-open the figure and confirm each row's attribution actually sits on the element you cited.** This is the teeth: the map is not done until every row is figure-verified.
  Record the finished map in `spine.md` (see **Build the spine** below), which is handed to every perspective that touches the example so each references one *verified* attribution instead of re-deriving it and diverging. Skip the whole map for papers without such an example.

**Rename the work dir to the citation slug.** Build `{year}-{venue}-{short-title}` from the metadata (see **Naming convention**) and rename the provisional work dir to `<dir>/<slug>/`; use the renamed path as `<WORK_DIR>` for the overview, Phase 2, and Finalize. Skip the rename if the dir is already so named (re-run). If a *different* directory of that name already exists, do not clobber it — keep the provisional name, note the collision, and continue.

**Build `<WORK_DIR>/paper.bib`** — the paper's own citation, dblp-verified like every other bibliographic fact (never hand-typed from memory):
1. Run `bash <SKILL_DIR>/scripts/dblp_lookup.sh "<title> <first-author surname>"`. Pick the hit whose title/authors/year match the paper; when both a peer-reviewed venue and a CoRR/arXiv preprint (`type` = "Informal and Other Publications") match, prefer the peer-reviewed one.
2. On a confident match: `bash <SKILL_DIR>/scripts/dblp_bibtex.sh "<key>" > <WORK_DIR>/paper.bib` (the `key` field from step 1).
3. On no confident match, or if `dblp_bibtex.sh` fails: hand-build a minimal entry from the paper's **printed** metadata only — cite key = the work-dir slug; `@inproceedings` / `@article` / `@misc` by venue kind; fields limited to `author`, `title`, `year`, plus `booktitle`-or-`journal` / `doi` / `url` that actually appear in the paper — and prepend a comment line `% not dblp-verified — from the paper's printed metadata`. Never invent a venue, DOI, or URL.

**Build `<WORK_DIR>/source-structure.md`** — the canonical source-topology
artifact used by reading-site authoring. Materialize the section map as one row
per real paper heading, in source order:

```markdown
# Source structure (canonical)

## Headings
- [pNN] L<level> | <source-form title, verbatim>
```

Include only headings present in the paper, including unnumbered source sections
such as Abstract or References when printed as headings. Do not include Ochiai
questions, perspective names, report headings, or any other explanatory structure
introduced by this pipeline. `source-structure.md` answers which divisions the
paper has; `spine.md` separately answers which confirmed facts downstream reports
must share.

**Build `<WORK_DIR>/spine.md`** — the paper's confirmed facts, materialized once as a durable artifact. This is the pipeline's single source of truth: it is handed to *every* perspective in Phase 2 (so they reference one confirmed value instead of independently re-deriving it and diverging) **and** it is the oracle the Finalize sweep checks every report against. The failure this prevents is concrete: without a materialized spine, a "handed-down" fact degrades into prompt-only hearsay that each isolated writer re-derives from OCR prose, and the reports diverge until reconciled by hand. Record it as a short Markdown file with these sections (include a section only if the paper has that kind of fact; keep each entry one line with its `[pNN]`):

- **Thesis + direction** — the paper's leading verdict in one sentence (a superiority / asymmetry / trade-off), with its direction fixed against the Abstract's own ordering (which side is stronger / which of two things holds more, in the paper's enumeration order). This supersedes the ad-hoc "thesis hand-down" — background and the overview both take the thesis from here.
- **Future-direction / practical-solution conclusion** — if the paper names a recommended direction or a "practical sweet spot" (e.g. which of several designs it endorses), state which one and why. This is the class an overview has independently re-derived and gotten wrong; pin it once.
- **Running-example map** — the figure-verified feature → concept/label table built above (with its evidence column and `[pNN]`), if the paper has such an example.
- **Headline numbers + scope** — each key result with its scope: the definition / setting it holds under, its population (all N, or a named subset "among the K …"), and whether it is a bound / mean / median / quantile. Label subset averages explicitly so a later report cannot juxtapose one with a whole-set average as if the denominator matched.
- **Figure-verified facts** — any other load-bearing fact read off a figure/table that more than one report will restate (a monotonic direction, an axis ordering, a value like "the CDA is `id`"), each anchored to the figure element it was read off. These carry the same single-source risk as the running-example map, so figure-verify them here.
- **Entity / system-class definitions** — pin any load-bearing class or entity name whose polarity could invert when a report compresses it into a table cell or a phrase, stating the definition *with its negation explicit* (e.g. "one-shot-only system = a system that does **not** support interactive transactions"). This is the authoritative source a report or the Finalize sweep resolves a cell's class polarity against, so a negated class name that reads fluently either way ("system that does not support X") cannot be silently reversed. Include only classes that more than one report uses or that carry a negation.

Build the spine against ground truth (the figures/tables and the Abstract's own sentences), not against a plausible mental model — an error here propagates to every report and no cross-report check can catch it (they will agree, on the wrong thing); only the Finalize sweep's re-verification against the source can. For a short paper with no running example and few shared numbers, the spine may be a handful of lines — build it anyway; it is what makes the sweep checkable.

**Write `reports/overview.md`** following the template below, in the conversation language (or the user's requested language). Take the thesis, the future-direction conclusion, and every headline number (with its scope) **from `spine.md`**, not by re-deriving them here. Rules:
- **Follow each item's writing discipline** (the bracketed guidance in the template). The Ochiai format's value is the sharpness of its six questions — a vague, adjective-laden answer wastes it. Concretely: item 1 must contain a one-sentence "X は Y する Z である" definition; item 2 must name the specific prior methods the paper compares against (never anonymous "既存手法"); item 4 must give numbers (`<baseline> 比 +N% on <benchmark>`), not "大幅に改善".
- **Surface the paper's own thesis, not only per-item facts.** The six questions decompose the paper side by side, so its own overall verdict — the judgment that ties several results together (a superiority / asymmetry / trade-off conclusion, usually the Abstract's "we show / reveal / find that …" sentence) — has no dedicated item and is easily lost as a list of separate numbers. Put the thesis **as fixed in `spine.md`** (already extracted from the Abstract's claim sentence, with its direction verified there) into the TL;DR (or a closing 総括 line); when several results are reported, keep the *relation* the paper draws between them (which is stronger, under what condition, at what cost), not just the individual values — that relation is the finding, and it must point the same direction as the spine (which side is stronger / which of two things holds more, in the paper's own ordering). *Why:* each item-answer can be correct yet the summary still omits the conclusion the paper leads with — or states that conclusion in the wrong direction; taking it from the spine keeps the overview and the detail reports on the same verdict.
- **Give every headline number its scope — and never juxtapose a subset average with a whole-set one unlabeled.** Write each key result with the conditions under which it holds: the method / definition / setting it is measured under, its population (all cases, or a named subset), and whether it is a bound / mean / median / quantile. Operationally, when you list several per-unit averages together, check for each whether its denominator is all N units or a named subset ("among the K … that have it") and label the subset ones explicitly; do not put a whole-set average and a subset average in the same bullet or sentence as if they shared a denominator. *Why:* a scopeless number reads as a universal fact and drops the condition that is often the paper's actual point (e.g. that the result depends on which definition is used); and an unlabeled subset average sitting next to a whole-set one is read on the same scale — this is the scope slip that most often regresses even when the rule is known.
- **Preserve the authors' hedges; don't harden them into fact.** Keep author modality — "can / may / suggests / we believe" — and present a design argument or hypothesis as such, not as a measured result (items 3–5 especially). Apply this (and the scope rule above) to **every claim-bearing locus, not just the flowing prose** — a table cell, a bullet, a figure/diagram caption, a callout — with the same strength: do not let a bullet or a caption assert as measured what the paragraph beside it correctly hedges. *Why:* the overview is the most-read layer, so a hedged or design-level claim asserted here as established fact misleads exactly the readers who never open the detail reports; and the discipline is easy to apply in the prose and easy to skip on the structural loci written around it, which is exactly where the hardening then survives.
- **Anchor the item-3 intuition's direction to the paper's own figure.** When the "why it works" intuition describes a trend, trade-off, or monotonic relation ("the finer the X, the more Y"), fix its direction from the paper's figure/table that quantifies it — not from a plausible-sounding mental model. *Why:* the intuition is written to be memorable, so an inverted-but-plausible trend here becomes the reader's takeaway and silently contradicts `method.md`, which reads the same figure; both layers only agree if each anchors to the source, not to intuition.
- **Key figure:** place the paper's single most explanatory figure — usually its Fig. 1 architecture/overview diagram, from `ocr/figures/` — right after the metadata block, with a one-line caption and its `[pNN]`.
- Items 1–2 (何を提案 / 新規性) point to `background.md`; items 3–6 each point to their own detail report — only for reports in Step 0 scope.
- Item 6 needs dblp-verified entries, which Phase 2 produces — leave it as `(Phase 2 完了後に確定)` for now and complete it at Finalize. If related-work is out of scope, instead pick 1–3 entries from the References section and verify them yourself with `bash <SKILL_DIR>/scripts/dblp_lookup.sh "<title> <first-author surname>"` before writing them (include the surname — title-only queries for generic titles miss the right paper).
- Close with **前提知識** and **原文の読み方** (both short), then the section map for source traceability.
