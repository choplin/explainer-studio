# Reviewing a generated document against the contract

The failures this catches **do not break the page**. A `::: {.callout variant=tip}`
around a warning generates a perfectly good green box; a `.keypoints` filled with an
introduction generates a perfectly good takeaways box. Nothing errors, nothing looks
broken, and the document quietly says something other than what it means.

That is why this is a review and not a linter. **Whether a class exists is nearly
worthless to know; whether it was used as intended is the whole question** — and
answering it requires reading what the markup says and comparing it to what the
prose says. Only a reader can do that.

**What you review is the IR.** The standard path generates the HTML deterministically
from a semantic IR (Markdown + fenced divs — `::: {.callout variant=danger}`), so the
markup claim to judge lives in the IR directive, and that is what you read. The
generator has already made the *mechanical* contract unbreakable — an unknown variant
fails the build, every table is wrapped, and an invented class or inline color cannot
be authored (raw HTML is dropped) — so those are **not findings here**. Everything
below is the *semantic* half: markup that builds cleanly and can still say the wrong
thing. A page produced by the **hand-authored fallback route** has no such guarantee;
when reviewing one, the checks marked *fallback only* below come back into scope.

## Inputs

- The **document(s)** to review: the **IR** source (`.md` with fenced divs) the page
  is generated from — that is where the markup claims live. On the hand-authored
  fallback route there is no IR: review the `.html` directly and re-include the
  *fallback only* mechanical checks below.
- The **contract**: the `understanding-html-docs` reference site. Read
  `SKILL.md`'s *Semantics → element / class* index and *Forbidden* list first; for a
  close judgment, read the reference pages themselves — `components.html` (what each
  component is *for*), `color.html` (what each hue means), `contract.html` (the
  rules).
- Optionally, a **consumer context contract**: a document generated by a skill that
  layers its own semantic axes on top of the base (e.g. `understanding-explain-diff`'s
  risk / change / verify axes) may come with that consumer's own contract — a short
  spec of what its IR directive attributes and custom classes mean. When supplied, review
  the document against it too (see check 8). When absent, review the base layer only.

Locate the base skill's directory before starting. If it cannot be found, stop and
say so — reviewing against a half-remembered contract is worse than not reviewing.

## What to check

Read the document, and for each item below ask *what the markup claims* versus *what
the content actually is*. Cite `file:line` for every finding.

### 1. Does each callout's variant match what it says?

The variant is a claim about the content. Check each `::: {.callout variant=…}`
against its own text (a bare `::: {.callout}` claims *note*):

| The text is… | The variant must be |
|---|---|
| A hazard, a destructive step, something that breaks | `danger` |
| Something to be careful about, a caveat | `warn` |
| Advice worth following, a recommendation | `tip` |
| The central insight of the section | `key` |
| Supporting information, everything else | `.callout` (bare = note) |

Also ask the prior question: **should this be a callout at all?** A callout
interrupts. A remark that merely adds context belongs in `.aside` or in the prose. A
document where every third paragraph is a callout has stopped using the emphasis it
is spending.

*Why this first:* a wrong variant is the single most common way meaning and markup
come apart, and it is invisible — the box renders beautifully in the wrong color, and
the reader takes the wrong signal.

### 2. Is `.keypoints` actually the takeaways?

`.keypoints` claims "this is what the section boils down to". Check that its content
is a distillation of the surrounding section, not an introduction, a summary of the
whole document, or a list that happened to need a box. If the section's substance is
not in it, the box is lying.

### 3. Is color carrying meaning, and only meaning?

- A meaning hue (`tip`/`warn`/`danger`/`key`, `[…]{.mark}`) used for **emphasis or
  decoration** — because red is eye-catching, not because the thing is dangerous.
- `[…]{.mark}` on a phrase that is not actually load-bearing.
- **No position-coding.** Chapters and sections do not get their own hues.
- *Fallback only* — a color reached for **outside the token layer**: a raw hex or
  `rgb()` in a `style` attribute or in a hand-written `<style>` block. It bypasses the
  theme and breaks in dark mode. On the IR path this is unrepresentable (raw HTML is
  dropped and there is no inline `<style>` to author), so check it only when reviewing
  hand-authored HTML.

### 4. Are the classes the contract's classes? — *fallback only*

On the IR path this cannot fail: an unknown `variant=` (`warning`, `error`, a typo) is
a **hard build error**, and an invented class or a raw class attribute cannot be
authored because raw HTML is dropped. Review it only on the hand-authored fallback
route, where names from *other* systems are the trap — `warning`, `error`, `info`,
`success` do not exist in this contract, and writing one renders a plain note instead
of failing. (Every class token must appear in the contract's index, or be defined in a
consumer stylesheet, or be an engine-contract class from a shipped component's
`include.md`.)

### 5. Do the headings mean "section"?

The `##` / `###` headings are the document's structure — the table of contents and the
reading-progress bar are built from them. Flag a heading used to make a line bold, and
a real section that was never given a heading (so it is invisible to the TOC). This is
a reading judgment and stays in scope on every route.

*Fallback only* — the `base.js` preconditions (at least one `h2`, headings inside the
first `main > article`, a `header.site` for the theme button). On the IR path the
generator owns that skeleton, so it is guaranteed. Check it only on the hand-authored
route — and there, a page that deliberately does **not** load `base.js` is not in
violation: those are the preconditions of a kit it opted out of, and the contract does
not constrain document structure.

### 6. Is the markup honest about what the content is?

- A `>` blockquote for an actual quotation from a source — not for a remark of the
  author's own (that is `::: {.aside}`).
- `[…]{.chip}` for a tag, `[…]{.badge}` for a status or count — not swapped for their
  looks.
- A Markdown table for genuinely tabular data, not laid out to fake a grid. Its
  `.tablewrap` is added by the generator — do not look for a missing wrapper (on the IR
  path there cannot be one); judge only whether the content is really a table.

### 7. Tier 2: does what is used actually render?

If the document renders a mermaid diagram, a git diff, or highlighted code, the
matching `assets/components/<name>/` bundle must be shipped alongside the generated
page, and a diff block must hold a **valid unified diff**. A missing bundle does not
error: the reader gets the raw source instead of the diagram. The content judgment
(is this actually a valid diff?) reads from the IR; the bundle-presence check is
verified against the generated output directory.

### 8. If a consumer context contract was supplied: do its own axes hold?

Only when a consumer contract was given (see Inputs). The consumer defines extra
semantic axes on top of the base — carried by **IR directive attributes** (e.g.
`::: {.change risk=high reason="…"}`) that its own chained filter renders into markup
and hues. Read each directive that carries such an axis and ask the same
variant-vs-content question as check 1, but against the consumer's contract:

- Does the value match the content? e.g. for `understanding-explain-diff`: a chunk
  marked `risk=low` that actually changes behavior; a `tested=yes` whose named test
  does not cover the chunk; a `verified` mark on a claim the document did not actually
  confirm; an inferred-background note dropped when the background really was inferred
  (or kept when real context was given).
- Is the axis mapped onto the hue its contract assigns, and nowhere else? The consumer
  reuses base hues by meaning (risk → `--bad`/`--warn`/`--tip`, change →
  `--muted`/`--accent`); flag a before/after painted in a risk hue, or vice versa.

These are exactly the "renders perfectly, means the wrong thing" failures — the base
reviewer is blind to them because the axes are the consumer's, not the base's. Skip
this check entirely when no consumer contract was supplied.

## Report

Return findings only — do not edit the document. Cite the **IR** `file:line` (or the
`.html` on the fallback route). For each:

```
<file>:<line>  [dimension]  what the markup claims → what the content actually is
               → the change to make
```

Rank by how badly the reader is misled: a wrong callout variant or a decorative
meaning-color outranks a swapped chip/badge. State plainly when a dimension came back
clean; a review that reports nothing and says nothing is indistinguishable from a
review that was never run.

If the document is long, review it whole rather than sampling — the errors here are
local and independent, so a sample misses exactly the ones it did not look at.

## Gotchas

- **Do not rewrite the document.** This skill reports; the generating skill fixes.
- **Do not report what the generator already prevents.** On the IR path a nonexistent
  class, an unwrapped table, an unknown variant, or an inline color cannot occur —
  flagging one means you are reviewing the wrong artifact (or it is the *fallback only*
  route, where those checks apply).
- **Do not review the prose.** Whether the writing is good is a different question.
  This is about whether the markup tells the truth about the prose.
- **Judge against the contract, not taste.** If a choice is defensible under the
  contract, it is not a finding — say so and move on.
